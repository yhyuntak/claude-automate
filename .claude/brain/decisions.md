## 상세

### mode 파일 포맷

**날짜**: 2026-02-27

**결정**: `.claude/state/mode` 파일에 단순 문자열만 저장 (`idle`, `planning`, `implement`)

**배경**: 세션 mode를 hook 스크립트와 커맨드 간에 공유할 방법 필요

**대안**:
- JSON 포맷: `{"mode": "planning", "since": "2026-02-27T10:00:00"}`
- 단순 문자열: `planning`

**결정 근거**:
- 단순 문자열이 읽기/쓰기 모두 간단 (`cat`, `echo` 사용 가능)
- JSON은 jq 없는 환경에서 파싱이 번거로움
- timestamp 등 추가 정보는 현재 필요 없음

**트레이드오프**:
- 단순성 ↑, 확장성 ↓ (추후 메타데이터 추가 시 포맷 변경 필요)

### plan 경로 저장 방식

**날짜**: 2026-02-27

**결정**: 현재 진행 중인 plan 경로를 mode 파일에 저장하지 않고, 필요 시 `grep -l "status: in_progress" .claude/plans/*.md`로 탐색

**배경**: `/implement` 커맨드에서 현재 진행 중인 plan 파일을 찾아야 함

**대안**:
- mode 파일에 경로 저장: `planning:.claude/plans/2026-02-27-feature.md`
- grep으로 탐색: `grep -l "status: in_progress" .claude/plans/*.md`

**결정 근거**:
- plan 파일 자체에 이미 `status: in_progress` 필드가 존재
- mode 파일에 경로 저장 시 plan 파일 이동/삭제 시 불일치 발생 가능
- grep 탐색은 항상 실제 상태 기준으로 찾으므로 일관성 보장
- 중복 저장 불필요

**트레이드오프**:
- 일관성 ↑, 탐색 속도 ↓ (plans 파일 수가 많아지면 grep 느려질 수 있음, 현재는 무시 가능)

### discovery-based 인덱스 포맷

**날짜**: 2026-02-27

**결정**: `docs/README.md` 인덱스를 고정 카테고리 없이 실제 존재하는 파일만 나열하는 포맷으로 작성

**배경**: `docs/` 폴더 인덱스를 어떤 방식으로 관리할지 결정 필요. 템플릿 기반(카테고리 미리 정의) vs discovery-based(실제 파일만 나열) 비교

**대안**:
- 템플릿 기반: 카테고리(API, 아키텍처, 가이드 등)를 미리 정의하고 해당 위치에 파일 추가
- discovery-based: 실제 존재하는 파일만 나열, 카테고리 없음

**결정 근거**:
- 다양한 프로젝트에 범용 적용 가능 (프로젝트마다 카테고리 구조가 다름)
- 미리 정의한 카테고리가 실제 콘텐츠와 맞지 않는 문제 방지
- 파일이 없는 빈 카테고리 섹션이 생기지 않아 인덱스가 항상 유효한 상태 유지

**트레이드오프**:
- 범용성 ↑, 일관성 ↓ (카테고리 구조가 없어서 프로젝트 간 인덱스 형태가 다를 수 있음)

### docs 스킬 Direct/Interview 모드

**날짜**: 2026-02-27

**결정**: `skills/docs/` 스킬이 인자/프롬프트 유무에 따라 두 가지 모드로 동작

- **Direct 모드**: 인자/프롬프트가 있을 때 → 히스토리에서 내용 추출하여 즉시 문서 생성
- **Interview 모드**: 인자/프롬프트가 없을 때 → 사용자에게 질문하여 내용 수집 후 문서 생성

**배경**: `/planning` 커맨드의 Direct/Interview 패턴이 UX 측면에서 효과적임을 확인. docs 스킬에도 동일 패턴 적용

**대안**:
- 항상 Interview 모드: 항상 사용자에게 질문
- 항상 Direct 모드: 항상 히스토리에서 추출 (인자 필수)
- Direct/Interview 혼합: 인자 유무로 자동 분기

**결정 근거**:
- `/planning` 패턴 차용으로 일관된 UX 제공
- 히스토리 컨텍스트가 있을 때 자동 추출이 사용자 입력 부담 감소
- 새 세션이나 컨텍스트 없을 때 Interview로 fallback하여 유연성 확보

**트레이드오프**:
- UX ↑, 구현 복잡도 ↑ (두 가지 분기 처리 필요)

### GPU 서버 동기화 전략 (2026-02-27)
- **결정**: rsync(글로벌 설정) + plugin install(플러그인) 방식 채택
- **대안**: 세션 히스토리 포함 전체 마이그레이션
- **이유**: 세션 히스토리는 경로 의존적(/Users vs /home)이라 마이그레이션 리스크 높음. 설정+플러그인만 동기화하면 plugin install로 환경 통일 가능
- **트레이드오프**: 과거 세션 히스토리 포기 ↔ 안정적 환경 구축

# 조합 1: 자율 하네스 (Autonomous Harness)

> 에이전트가 스스로 협업하고, 동적으로 생성되며, 경험으로부터 학습하는 하네스

---

## 개요

**자율 하네스**는 메인 컨텍스트의 개입을 최소화하고, 에이전트들이 스스로 통신하고 협업하며, 필요에 따라 동적으로 생성/해체되고, 작업 결과로부터 자동으로 규칙을 개선하는 시스템입니다.

한 마디로: **"메인은 방향만 제시하고, 실행과 학습은 에이전트 생태계가 자율적으로"**

---

## 영감 (Sources)

### Kimi K2.5 Agent Swarm
- **동적 에이전트 생성**: 작업에 맞춰 필요한 에이전트를 즉시 생성
- **독립 Working Memory**: 각 에이전트가 자신만의 메모리 공간 보유
- **PARL (Policy Adaptive Reinforcement Learning)**: 오케스트레이터가 작업 성과로부터 학습

### Claude Code Agent Teams
- **Mailbox 통신**: 에이전트끼리 직접 메시지를 주고받음
- **공유 Task List**: 작업 상태를 공유하며 협업

### Opus 4.6
- **끈기 있는 작업**: 실패해도 재시도하며 목표 달성
- **구현 우선**: 계획보다 실행을 우선시하는 성향

## 각 구성요소 설명

### 1. Mailbox: 에이전트 간 직접 통신

**기존 방식 (claude-automate)**:
```
Agent A → 작업 완료 → Main
Main → 결과 확인 → Agent B에게 전달
```

**Mailbox 방식**:
```
Agent A → Mailbox → Agent B
(Main은 모니터링만)
```

**왜 필요한가?**
- 메인 컨텍스트 오염 방지
- 빠른 협업 (메인을 거치지 않음)
- 에이전트 간 context sharing 효율적

**작동 방식**:
```
Architect:
  "설계 완료. Implementer에게: User 모델은 /models/User.ts에 정의"

Mailbox:
  From: Architect
  To: Implementer
  Message: { design: "...", modelPath: "/models/User.ts" }

Implementer:
  Mailbox에서 메시지 읽음 → 구현 시작
```

### 2. Dynamic Agent Factory: 작업 기반 에이전트 생성/해체

**기존 방식**:
```
미리 정의된 에이전트들 (Architect, Writer, Tester, ...)
모든 작업에 항상 동일한 에이전트 세트 사용
```

**Dynamic Factory 방식**:
```
작업 분석 → 필요한 에이전트만 생성 → 작업 완료 → 해체
```

**생성 트리거 예시**:
```
상황: "회원 인증 구현"
분석:
  - 설계 필요 → Architect 생성
  - 보안 이슈 → Security Expert 생성
  - 구현 필요 → Implementer 생성
  - DB 마이그레이션 필요 → DB Migrator 생성

상황: "버그 수정"
분석:
  - 디버깅 → Debugger 생성
  - 수정 → Implementer 생성
  - (설계는 불필요 → Architect 생성 안 함)
```

**해체 타이밍**:
```
Tester의 작업이 완료되고, 다른 에이전트가 더 이상 Tester를 필요로 하지 않으면
→ Tester 해체 (Working Memory 보관)
```

### 3. Working Memory Isolation: 에이전트별 독립 메모리

**왜 필요한가?**

에이전트가 작업한 모든 내용을 메인 컨텍스트에 보고하면:
- 메인 컨텍스트가 빠르게 오염됨
- 불필요한 정보까지 포함됨

독립 메모리를 사용하면:
- 각 에이전트는 자신의 작업 컨텍스트만 관리
- 필요한 정보만 Mailbox로 공유
- 메인은 요약만 받음

**구조**:
```
Architect Working Memory:
  - 설계 문서
  - 아키텍처 결정 히스토리
  - 관련 파일 경로

Implementer Working Memory:
  - 구현한 코드
  - 참고한 라이브러리
  - 발생한 이슈

Main Context:
  - 전체 목표
  - 현재 진행 상황 (요약)
  - 최종 결과
```

**보관 정책**:
```
에이전트 해체 시:
  - Working Memory는 압축하여 보관
  - 나중에 동일 유형 에이전트 생성 시 재사용 가능
```

### 4. Self-Evolving Rules: 경험 기반 규칙 자동 조정

**기존 방식**:
```
규칙은 사람이 직접 작성하고 수정
```

**Self-Evolving 방식**:
```
작업 결과 분석 → 규칙 가중치 자동 조정
```

**가중치 조정 예시**:

작업 결과:
```
Task: "회원 인증 구현"
에이전트: Architect → Implementer → Tester
결과: 성공, 버그 0개, 시간 30분

Task: "알림 기능 구현"
에이전트: Implementer (Architect 없이)
결과: 성공, 버그 3개, 리팩토링 필요

Task: "대시보드 구현"
에이전트: Architect → Implementer → Reviewer
결과: 성공, 버그 0개, 코드 품질 높음
```

규칙 조정:
```
Before:
  architect_priority: 0.5
  reviewer_priority: 0.3

After (학습 반영):
  architect_priority: 0.7  (Architect 있을 때 버그 적음)
  reviewer_priority: 0.6   (Reviewer 있을 때 품질 높음)
```

**조정 대상**:
- 에이전트 생성 우선순위
- 에이전트 조합 선호도
- Tier 선택 (Haiku/Sonnet/Opus)
- Mailbox 메시지 전달 규칙

## 시너지: 왜 1+1+1+1 > 4인가?

### 1. Mailbox + Dynamic Factory
```
빠른 협업 (Mailbox) × 필요한 에이전트만 생성 (Factory)
= 최소한의 에이전트로 최대 효율
```

**예시**:
```
Architect가 설계를 완료하면
→ Mailbox로 Implementer에게 즉시 전달
→ Implementer가 바로 구현 시작
→ 구현 중 Security Expert 필요 감지
→ Factory가 Security Expert 동적 생성
→ Security Expert가 Mailbox로 조언 전달
→ 작업 완료 후 Security Expert 해체
```

### 2. Working Memory + Mailbox
```
독립 메모리 (WM) × 선택적 공유 (Mailbox)
= 메인 컨텍스트 보호 + 효율적 협업
```

**예시**:
```
Implementer의 Working Memory에는:
  - 시도한 모든 코드 (100줄)
  - 참고한 라이브러리 문서 (1000줄)

Mailbox로 Tester에게 전달:
  - 최종 코드 (20줄)
  - 테스트해야 할 케이스 (10줄)

→ Tester는 필요한 정보만 받음
```

### 3. Self-Evolving + Factory
```
규칙 자동 조정 (Evolving) × 동적 생성 (Factory)
= 계속 똑똑해지는 에이전트 생태계
```

**예시**:
```
초기:
  복잡한 작업에도 Architect 생성 안 함 (우선순위 낮음)
  → 버그 많이 발생

학습 후:
  architect_priority: 0.5 → 0.8
  → 복잡한 작업에 Architect 자동 생성
  → 버그 감소
```

### 4. 전체 조합
```
자율적 협업 (Mailbox + WM) ×
필요 기반 생성 (Factory) ×
경험 학습 (Evolving)
= 사람 개입 최소화 + 계속 개선되는 시스템
```

## 트레이드오프

### 장점

1. **메인 컨텍스트 보호**
   - 에이전트 협업 세부사항이 메인을 오염시키지 않음
   - 메인은 전략적 사고에 집중 가능

2. **효율적 자원 사용**
   - 필요한 에이전트만 생성 → API 비용 절감
   - 독립 메모리 → 컨텍스트 크기 최소화

3. **빠른 협업**
   - 에이전트 간 직접 통신 → 지연 감소
   - 병렬 작업 효율 증가

4. **자동 개선**
   - 사용할수록 똑똑해짐
   - 프로젝트마다 최적화됨

### 위험

1. **복잡성 증가**
   - 4가지 시스템의 조합 → 디버깅 어려움
   - 예상치 못한 상호작용 가능성

2. **예측 불가능성**
   - Self-Evolving Rules → 규칙이 어떻게 변할지 모름
   - 의도하지 않은 방향으로 학습할 가능성

3. **초기 성능**
   - 학습 데이터 없는 초반에는 오히려 비효율적
   - 충분한 작업 이력 필요

4. **투명성 감소**
   - 에이전트 간 직접 통신 → 사람이 흐름 파악 어려움
   - Working Memory 독립 → 전체 상황 파악 힘듦

### 현실적 우려

1. **API 비용**
   - 에이전트 간 메시지도 API 호출 → 비용 증가 가능
   - 불필요한 통신 최소화 필요

2. **디버깅**
   - "왜 이 에이전트가 생성되었지?"
   - "왜 이 규칙이 변경되었지?"
   - → 로깅/모니터링 시스템 필수

3. **안정성**
   - 잘못된 학습으로 시스템 전체가 비효율적으로 변할 위험
   - Rollback 메커니즘 필요

## 다음 단계 (참고용)

실제 구현을 고려한다면:

### Phase 1: Mailbox (기반)
- 에이전트 간 통신 프로토콜 정의
- Task Tool 확장하여 메시지 큐 구현
- 간단한 2-agent 협업 테스트 (Architect ↔ Implementer)

### Phase 2: Working Memory (효율화)
- Task metadata로 에이전트별 메모리 격리
- 요약 전략 구현 (메인에 보고할 내용 선별)
- 메모리 압축/보관 로직

### Phase 3: Dynamic Factory (자동화)
- 에이전트 템플릿 시스템
- 생성 트리거 규칙 엔진
- 해체 및 재사용 로직

### Phase 4: Self-Evolving (학습)
- 성과 측정 지표 정의
- 가중치 조정 알고리즘
- 롤백 메커니즘

## 결론

**자율 하네스**는 claude-automate가 단순한 "에이전트 호출 도구"에서 **"스스로 협업하고 학습하는 에이전트 생태계"**로 진화하는 비전입니다.

**핵심 아이디어**:
- 메인은 방향만 제시
- 에이전트는 스스로 협업
- 경험으로부터 학습
- 필요한 것만 생성

**현실적 고려**:
- 복잡성 vs 효율성
- 예측 가능성 vs 자율성
- 초기 비용 vs 장기 이득

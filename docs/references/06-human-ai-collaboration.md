# 사람-AI 협업 극대화 (Human-AI Collaboration)

> 사람은 What/Why를 결정하고, AI는 How를 자율적으로 실행하는 구조

## 개요

이 문서는 세 가지 아이디어를 조합하여 사람과 AI의 역할을 명확히 분리하는 협업 구조를 제시합니다.

**핵심 컨셉**: 사람은 전략과 방향을 결정하고, AI는 계획과 실행을 자율적으로 수행합니다.

```
사람        AI Planner         AI Workers
 │              │                  │
What/Why  →  Plan/How  →  Implement/Validate
```

## 영감 (Sources)

이 조합은 세 가지 소스에서 영감을 받았습니다.

### 1. Claude Code Agent Teams

**핵심 기능**:
- **Plan Approval**: AI가 계획을 세우면 사람이 승인한 후 자율 실행
- **Delegate Mode**: 승인 후 AI가 자율적으로 작업 분배 및 실행
- **Task List**: 작업을 Task로 분해하고, 에이전트가 claim하여 실행

**인사이트**:
```
"계획-승인-실행"을 분리하면 사람은 전략에만 집중 가능
```

### 2. Kimi K2.5

**핵심 메커니즘**:
- **오케스트레이터**: 전체 구조를 파악하고 작업을 분해
- **계층적 Task 분해**: 큰 작업을 high/medium/low level로 쪼갬
- **자율 실행**: 분해된 Task를 자율적으로 claim하고 실행

**인사이트**:
```
"전체 파악 → 분해 → 자율 실행"의 3단계 구조
```

### 3. Opus 4.6 특성

**핵심 차별점**:
- **적극적 의견 제시**: 수동적으로 기다리지 않고 먼저 제안
- **전체 구조 파악 선행**: 세부 실행 전에 큰 그림 먼저
- **전략적 사고**: How뿐 아니라 Why도 고민

**인사이트**:
```
"Opus는 Planner 역할에 최적화되어 있다"
```

## 핵심 철학

### 역할 분리

```
┌──────────────────────────────────────────────────┐
│              사람 (Driver)                        │
│         What + Why를 결정                         │
│   "사용자 인증 시스템이 필요해"                      │
└──────────────────────────────────────────────────┘
                      │
                      ▼
┌──────────────────────────────────────────────────┐
│           AI Planner (Opus)                       │
│         How를 계획 + 제안                          │
│   "JWT/OAuth 중 선택, DB 스키마, 파일 구조 제안"     │
└──────────────────────────────────────────────────┘
                      │
                      ▼ (사람 승인)
                      │
                      ▼
┌──────────────────────────────────────────────────┐
│         AI Workers (Sonnet/Haiku)                 │
│         계획대로 구현 + 검증                        │
│   "Task별로 claim하여 병렬 실행"                    │
└──────────────────────────────────────────────────┘
```

### 신뢰의 계층

이 구조는 "신뢰할 수 있는 부분"을 명확히 분리합니다.

| 역할 | 신뢰 방식 | 보호 장치 |
|------|----------|----------|
| 사람 | 최종 결정권자 | 계획 승인/거부 |
| Planner (Opus) | 계획 자율성 | 사람의 승인 필요 |
| Workers (Sonnet/Haiku) | 실행 자율성 | 계획 범위 내에서만 |

```

    │
    ├─→ Task 2 (Medium) - UserService 구현
    │       │
    │       └─→ Task 4 (Low) - 테스트
    │
    └─→ Task 3 (Medium) - AuthController 구현
            │
            └─→ Task 5 (Low) - 문서 작성

Task 1 완료 전에는 Task 2, 3 claim 불가 (blockedBy)
Task 2 완료 후 Task 4 자동 claim 가능
```

## 각 구성요소 설명

### 1. Plan Approval: 계획-승인 분리

**왜 중요한가?**

사람이 모든 세부사항을 지시하는 것은 비효율적입니다. 하지만 AI에게 완전히 맡기면 방향이 엇나갈 수 있습니다.

**해결책**:

```
AI가 계획을 세우되, 사람이 승인해야만 실행
```

**워크플로우**:

1. **Planner**가 계획안 작성
2. 사용자에게 제시 (EnterPlanMode)
3. 사용자 승인 → Delegate Mode 진입
4. 사용자 거부 → 수정 후 다시 제시

**장점**:

- 사람은 What/Why에만 집중
- AI는 How를 자율적으로 고민
- 사람은 최종 검증만 수행

### 2. 계층적 Task 분해

**왜 필요한가?**

큰 작업을 한 번에 처리하면 복잡도가 폭발합니다. 작은 단위로 쪼개야 합니다.

**3-Level 분해**:

| Level | 역할 | 담당 Tier | 예시 |
|-------|------|----------|------|
| High | 아키텍처, 전략적 결정 | Opus | "인증 방식 선택", "DB 스키마 설계" |
| Medium | 핵심 로직 구현 | Sonnet | "UserService 구현", "API 엔드포인트" |
| Low | 데이터 수집, 문서화 | Haiku | "테스트 데이터 생성", "README 작성" |

**분해 원칙**:

- Top-down: 큰 Task부터 작은 Task로
- 의존성 명시: blockedBy/blocks 관계 설정
- 병렬 가능성: 독립적인 Task는 병렬 실행

**예시**:

```
"사용자 인증 시스템"
  ├─ High: 인증 방식 결정 (JWT vs OAuth)
  ├─ High: DB 스키마 설계
  │
  ├─ Medium: User 모델 구현 (blockedBy: 스키마)
  ├─ Medium: AuthService 구현 (blockedBy: 스키마)
  │
  ├─ Low: 테스트 데이터 생성 (blockedBy: 모델)
  └─ Low: API 문서 작성 (blockedBy: AuthService)
```

### 3. Hybrid Instance Model: Tier별 실행 전략

**왜 두 가지 방식이 필요한가?**

모든 작업을 subagent로 처리하면 메인 컨텍스트가 오염됩니다. 하지만 모든 작업을 독립 인스턴스로 처리하면 비용과 속도가 문제됩니다.

**Tier별 전략**:

| Tier | 실행 방식 | 이유 |
|------|----------|------|
| Haiku (Low) | Subagent | 빠르고 저렴, 컨텍스트 오염 적음 |
| Sonnet (Medium) | Subagent | 표준 작업, 메인과 통신 필요 |
| Opus (High) | 독립 인스턴스 | 복잡한 사고, 메인과 격리 필요 |

**독립 인스턴스가 필요한 경우**:

- 아키텍처 설계 (전체 구조 파악)
- 복잡한 알고리즘 (여러 시도 필요)
- 장기 실행 작업 (메인 블록 방지)

**Subagent로 충분한 경우**:

- 단순 구현 (명확한 입출력)
- 데이터 수집/변환
- 문서 작성

**현재 claude-automate와의 차이**:

```
현재: 모든 에이전트가 subagent
제안: High Tier만 독립 인스턴스, 나머지는 subagent
```

## 시너지: 3가지 조합의 효과

각 아이디어는 단독으로도 가치가 있지만, 조합하면 더 강력한 워크플로우가 됩니다.

### 단독 사용 시

| 아이디어 | 단독 효과 | 한계 |
|---------|----------|------|
| Plan Approval | 사람이 방향 제어 | Task 분해가 없으면 계획이 너무 큼 |
| 계층적 Task | 작업 분해 명확 | 승인 없이 실행하면 방향 엇나감 |
| Hybrid Instance | Tier별 최적화 | Task 구조 없이는 어느 것을 독립 인스턴스로 할지 불명확 |

### 조합 사용 시

```
Plan Approval + 계층적 Task + Hybrid Instance
       ↓              ↓              ↓
  방향 제어       작업 분해       효율적 실행
       └──────────┬──────────┘
                  ▼
         완전한 사람-AI 협업 구조
```

**워크플로우 예시**:

1. **사용자**: "사용자 인증 시스템 만들어줘" (What)
2. **Planner (Opus, 독립 인스턴스)**:
   - 전체 구조 파악
   - High/Medium/Low Task로 분해
   - 계획안 제시
3. **사용자**: 승인 (Why 확인)
4. **Delegate Mode 진입**:
   - High Task → writer-high (Opus, 독립 인스턴스)
   - Medium Task → writer (Sonnet, subagent) [병렬]
   - Low Task → explore-low (Haiku, subagent) [병렬]
5. **자율 실행**:
   - 각 에이전트가 Task claim
   - 검증 후 Task 완료
   - 의존성 해소 시 다음 Task claim
6. **사용자**: 결과 확인

## 현재 하네스와의 갭

### 현재 claude-automate 구조

```
메인 컨텍스트 (규칙 기반 오케스트레이터)
    ├─ explore-low/explore/explore-high (subagent)
    ├─ writer/writer-high (subagent)
    └─ pattern-checker, doc-sync-checker (subagent)
```

**특징**:
- 메인이 모든 결정 수행
- 에이전트는 실행만 담당
- Task 분해 없음 (사람이 직접 지시)
- Plan Approval 부재 (planning 스킬은 있지만 승인 메커니즘 없음)

### 제안 구조

```
사용자
    ↓
Planner (Opus, 독립 인스턴스)
    ↓ (Plan Approval)
사용자 승인
    ↓
Delegate Mode
    ├─ High Task → writer-high (Opus, 독립 인스턴스)
    ├─ Medium Task → writer (Sonnet, subagent)
    └─ Low Task → explore-low (Haiku, subagent)
```

**특징**:
- Planner가 계획 수립 (사람은 승인만)
- Task 자동 분해
- Tier별 실행 전략 (독립 인스턴스 vs subagent)
- 에이전트가 자율적으로 Task claim

### 갭 분석

| 요소 | 현재 | 제안 | 변경 필요 사항 |
|------|------|------|---------------|
| 계획 수립 | 사람 | Planner (Opus) | Planner 에이전트 추가 |
| 승인 메커니즘 | 없음 | Plan Approval | EnterPlanMode 연동 |
| Task 분해 | 없음 | 계층적 분해 | Task List 시스템 |
| 에이전트 호출 | 메인이 지시 | 자율 claim | Delegate Mode |
| Opus 사용 | subagent | 독립 인스턴스 | 실행 모델 변경 |

### 점진적 도입 경로

```
Phase 1: Plan Approval 추가
  - planning 스킬에 승인 메커니즘 추가
  - EnterPlanMode 활용

Phase 2: Task List 시스템
  - 계층적 Task 분해 로직
  - blockedBy/blocks 의존성 관리

Phase 3: Delegate Mode
  - 에이전트 자율 claim
  - 병렬 실행 관리

Phase 4: Hybrid Instance
  - Opus를 독립 인스턴스로 전환
  - Tier별 실행 전략 적용
```

## 트레이드오프

### 장점

1. **역할 명확성**
   - 사람: What/Why만 결정
   - AI: How를 자율적으로 처리
   - 책임 소재 명확

2. **효율성**
   - 병렬 실행 (독립적인 Task)
   - Tier별 최적화 (비용/속도)
   - 사람의 개입 최소화

3. **확장성**
   - Task 단위로 쪼개져 있어 추가 쉬움
   - 에이전트 교체 용이
   - 새로운 Tier 추가 가능

4. **신뢰성**
   - 계획 승인으로 방향 제어
   - 의존성 관리로 순서 보장
   - 검증 단계 포함

### 위험 및 단점

1. **복잡도 증가**
   - 시스템 구조가 복잡해짐
   - Task 분해 로직 필요
   - 의존성 관리 오버헤드

2. **초기 학습 곡선**
   - 사용자가 새 워크플로우 적응 필요
   - Plan Approval 거부 시 수정 과정
   - Task 분해 품질에 따라 효율 차이

3. **오버 엔지니어링 위험**
   - 단순한 작업에는 과도할 수 있음
   - 작은 프로젝트에서는 비효율
   - Task 분해가 너무 세밀하면 오버헤드

4. **Planner 품질 의존**
   - Planner가 잘못 분해하면 전체 실패
   - Opus 비용 증가 (독립 인스턴스)
   - 계획 수정 반복 시 시간 소요

5. **동기화 이슈**
   - 병렬 실행 시 충돌 가능
   - Task 간 데이터 공유 어려움
   - 의존성 설정 실수 시 데드락

### 적합한 경우 vs 부적합한 경우

**적합**:
- 중대형 프로젝트 (10+ 파일)
- 복잡한 기능 구현
- 여러 단계의 작업
- 방향이 명확하지 않은 경우

**부적합**:
- 간단한 버그 수정
- 파일 1-2개만 수정
- 명확한 작업 (바로 실행 가능)
- 빠른 프로토타이핑

## 핵심 질문

이 방향을 선택하면 다음 질문에 답해야 합니다.

### 1. Task 분해 기준

**질문**: "어떻게 High/Medium/Low를 구분할 것인가?"

**고려사항**:
- 복잡도? (LoC, 의존성 수)
- 중요도? (비즈니스 임팩트)
- 자율성? (결정 필요 여부)

**예시 기준**:
```
High: 아키텍처 결정, 기술 선택, 전략 수립
Medium: 비즈니스 로직, API 구현, 핵심 기능
Low: 데이터 수집, 문서화, 단순 변환
```

### 2. Plan Approval 인터페이스

**질문**: "어떻게 계획을 제시하고 승인받을 것인가?"

**옵션**:
- EnterPlanMode (현재 Claude Code 기능)
- AskUserQuestion (질문 형태)
- 별도 UI (터미널 인터페이스)

**트레이드오프**:
```
EnterPlanMode: 공식 기능, 안정적, 제약 있음
AskUserQuestion: 유연, 커스텀 가능, 비표준
별도 UI: 최고의 UX, 개발 비용 높음
```

### 3. Delegate Mode 구현

**질문**: "에이전트가 Task를 어떻게 claim하는가?"

**옵션 A**: 메인이 할당
```
메인: "Task 1은 writer-high, Task 2는 writer"
```

**옵션 B**: 에이전트가 자율 선택
```
에이전트: "내가 할 수 있는 Task는 2, 3입니다"
```

**트레이드오프**:
- 옵션 A: 안전, 예측 가능, 유연성 낮음
- 옵션 B: 효율적, 위험 높음, 로직 복잡

### 4. 독립 인스턴스 관리

**질문**: "독립 인스턴스를 어떻게 생성/관리/종료하는가?"

**기술 과제**:
- 인스턴스 생성 API
- 상태 추적 (실행 중/완료/실패)
- 결과 수집 및 통합
- 에러 핸들링

**비용 고려**:
- Opus 독립 인스턴스 = 높은 비용
- 언제 subagent로 대체 가능한가?

### 5. 에러 복구 전략

**질문**: "Task 실행 중 실패 시 어떻게 복구하는가?"

**시나리오**:
- High Task 실패 → 전체 중단? 수정 후 재시도?
- Medium Task 실패 → 다른 Task 영향?
- 병렬 실행 중 일부 실패 → 롤백? 계속?

**복구 옵션**:
```
1. 사람에게 문의 (안전, 느림)
2. Planner가 재계획 (자동, 위험)
3. 실패 Task만 재시도 (중간)
```

### 6. 점진적 도입 전략

**질문**: "기존 사용자에게 어떻게 전환시킬 것인가?"

**옵션**:
- Big Bang: 한 번에 모든 기능 도입
- Feature Flag: 옵션으로 제공, 점진적 활성화
- 별도 Command: `/automate` 등 새 진입점

**마이그레이션 고려**:
- 기존 워크플로우 호환성
- 문서 업데이트
- 학습 자료

### 7. 성공 지표

**질문**: "이 구조가 성공했다는 것을 어떻게 측정하는가?"

**후보 지표**:
- 사람의 개입 횟수 감소
- 작업 완료 속도
- 에이전트 재시도 횟수
- 사용자 만족도
- 비용 효율성

**트레이드오프**:
```
속도 vs 정확도
자동화 vs 통제
비용 vs 품질
```

## 결론

사람-AI 협업 극대화는 단순한 기능 추가가 아니라 **개발 방식의 전환**입니다.

**핵심 가치**:
```
사람은 What/Why에 집중
AI는 How를 자율 실행
둘 사이의 인터페이스는 "계획 승인"
```

이 조합은 Peter Steinberger의 "계획에 시간 투자, 실행은 위임", Kimi K2.5의 "계층적 분해", Opus 4.6의 "전략적 사고"를 통합합니다.

하지만 복잡도가 증가하고, 초기 학습 곡선이 있으며, 모든 프로젝트에 적합하지 않을 수 있습니다.

**도입 전 고민할 것**:
- 내 프로젝트 규모에 맞는가?
- 복잡도 증가를 감당할 수 있는가?
- 점진적 도입 경로는 무엇인가?

**이 문서는 구현 스펙이 아니라 개념 이해를 위한 참고 자료입니다.**
실제 도입 여부는 프로젝트 상황, 팀 구조, 비용을 고려하여 결정하세요.
